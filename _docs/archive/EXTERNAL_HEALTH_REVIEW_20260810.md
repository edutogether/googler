## Method
Same rubric used on a sibling project (codyssey): file-size/god-component scan, TODO/FIXME/HACK/@ts-ignore/eslint-disable grep, `any` usage grep, tsconfig strictness, test:source LOC ratio, actually running `vitest`/`eslint`/`tsc`, Firebase config/rules read, secrets-in-tree check, git/CI state.

## Findings (ranked)

1. **CRITICAL — the shipped app is disconnected from the tested/working architecture.** `App.tsx` renders `MainWorldV3` (`src/features/main-v3/MainWorldV3.tsx`), which imports only `WorldIcons` and its own CSS — no `createAppServices`, no Firebase, no domain/progress data, no course content. It's a static shell: `"320 / 560 XP"` and `"65%"` at line 247 are **hardcoded**, and most of its ~10 buttons just toast "이 길은 아직 준비 중이에요" (`MainWorldV3.tsx:161`). Meanwhile `src/legacy/LegacyGooglerApp.tsx` — which actually wires Firebase/preview services, real progress persistence, and `pages/*`, `features/learning/*`, `features/profile/ProfileEditor`, `content/courses.ts` — is imported by nothing except itself. **~1,607 of 1,910 non-test LOC (≈84%) are unreachable dead code.** This looks like an entry-point swap during a later visual reskin (commits `6192781`→`7eb7966`) that was never re-wired to the working logic. `docs/stage-0-validation.md` graded the pre-reskin architecture "B, 조건부 통과" — that graded work is now orphaned.
2. **No `firestore.rules` (or `firebase.json`) versioned anywhere in the repo.** Security policy isn't auditable or CI-checked. `firebaseServices.ts:16-19` signs in anonymously/via custom token with no server-side claim verification visible in code; writes are by client-supplied `uid` with no rule enforcement evident. README defers this to "Stage 1" — currently an unaudited trust boundary *if* Firebase were actually wired to the live UI (it currently isn't, per #1).
3. **`tsconfig.app.json` has `"strict": false`** — no `strictNullChecks`/`noImplicitAny`. `src/legacy/LegacyGooglerApp.tsx` has untyped handler params throughout (e.g. `selectedEmoji, nicknameInput`, `dayItem, index`, untyped `error`) that would fail under `strict: true`.
4. **Stale CI trigger.** `.github/workflows/ci.yml`'s `push` trigger targets `refactor/foundation-zero`, a branch that no longer exists (deleted after merge) — so CI's push-trigger path is currently dead. `deploy-pages.yml` deploys `main` on push with **no test/lint gate before deploy**.
5. Positives: zero TODO/FIXME/HACK/@ts-ignore/eslint-disable anywhere in `src`; zero explicit `any`; the **preview-mode fallback design is genuinely well-built** — `getFirebaseConfig()` (`src/data/firebase/config.ts:12`) returns `null` unless all six `VITE_FIREBASE_*` vars are set, `createAppServices()` (`src/data/createAppServices.ts:6-10`) falls back to in-memory `createPreviewServices()` cleanly behind one interface, no SDK leakage into UI. Secrets hygiene is clean (`.env*` gitignored, only `.env.example` tracked). Actually running things: `tsc -b` clean, `eslint .` clean, `vitest run` → 9 files / 25 tests, all passing (a much smaller suite than codyssey's 406, test:source ratio ~1:3.6). Currently on branch `feature/main-mobile-final-20260805`, working tree has uncommitted changes (image adds/deletes, `MainWorldV3.tsx/css/test.tsx`, `vite.config.ts`) plus 16 untracked PNGs.

## Bottom line
Code quality on what exists is clean by the usual markers, but the app currently in front of a user does not do what its own README/architecture docs claim — the well-tested, Firebase-wired implementation exists but is orphaned behind an unconnected entry point. This is the single most actionable finding across all apps reviewed today: the fix is re-wiring, not rewriting — the working logic already exists in `LegacyGooglerApp.tsx`.
